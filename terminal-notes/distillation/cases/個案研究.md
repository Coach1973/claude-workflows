## 個案一：Groq 限流死機（2026-04）

### 症狀
`All models are temporarily rate-limited`

### 根本原因
- Groq 上限 12,000 TPM
- 小龍蝦系統提示約 57,000 tokens
- 永遠 413 錯誤

### 修復
更換 Primary 模型為 TPM 上限更高的模型

### 學到的
接入新模型前，先確認 TPM 上限。Groq 只能跑小任務，不能當 Primary。

## 個案二：Session Lock 迷宮（2026-04-11）

### 症狀
`All models failed: Live session model switch requested: xxx (unknown)`

### 根本原因
JSONL 檔案未清除，gateway 從中恢復鎖定狀態。只清 sessions.json 不夠。

### 正確解法
```bash
# 1. 刪 JSONL + 清 sessions.json
# 2. 清 auth cooldown
# 3. 重啟 gateway
```

### 學到的
永遠要刪 JSONL，不只是清 sessions.json。

## 個案三：記憶失憶問題（2026-04-11）

### 症狀
小龍蝦每次重啟都是完全失憶狀態，多次重複交代同樣的事、搞錯帳號。

### 根本原因
AGENTS.md 規定啟動時讀 `memory/YYYY-MM-DD.md`，但 `memory/` 目錄從未被建立。

### 正確解法
```bash
mkdir -p /Users/bymyway/.openclaw/workspace/memory/
```

### 學到的
AGENTS.md 說的東西要逐項驗證，不能假設都已設定好。

## 個案四：Context Overflow 與書籤機制（2026-04-11）

### 問題
如果對話還沒半小時，對話框就滿了，中間那段不就遺失了？

### 解法
- 書籤記錄「哪個檔案存到哪一行」
- 溢出時從書籤接著存到最後一行
- 換新 session 時書籤自動歸零
- 結果：任何情況下都零遺漏

## 個案五：MiniMax API Key 格式

### 問題
MiniMax API Key 格式（`sk-cp-...`）不被 Claude Code CLI 認可為有效登入，導致「Not logged in · Please run /login」。

### 根本原因
Claude Code CLI 的 `BS()` 函數在讀取 MiniMax key 時，會走到 OAuth 登入檢查分支，不接受 `sk-cp-` 開頭的 key。

### 修復方法
在 `~/.claude/settings.json` 的 `env` 區塊加入 `ANTHROPIC_AUTH_TOKEN`（值同 MiniMax API key）：
```json
"ANTHROPIC_AUTH_TOKEN": "sk-cp-你的key",
"ANTHROPIC_BASE_URL": "https://api.minimax.io/anthropic",
"ANTHROPIC_API_KEY": "sk-cp-你的key"
```

### 原理
`ANTHROPIC_AUTH_TOKEN` 環境變數存在時，`BS()` 直接認定有登入，不做任何 key 格式驗證。

## 個案六：雙 API Key 輪替修復

### 問題
2026-04-17 凌晨，1號機小龍蝦反覆死機超過 12 小時。

### 根本原因：litellm cooldown_time 死鎖
```yaml
litellm_settings:
  cooldown_time: 60  # ← 元兇
```
死循環：
1. Google API 返回 429（配額超限）
2. litellm 將模型放入 60 秒冷卻期
3. 冷卻期間所有新請求立刻失敗（不等待、不重試）
4. 立刻失敗 → 觸發重置冷卻計時器
5. 永遠無法離開冷卻期 → bot 死機數小時

### 修復
移除 `cooldown_time`，改用 `retry_after: 60` + `num_retries: 10`

### 附加修復
申請第二把 API Key，實現雙 Key 輪替。

## 個案七：VPS MiniMax auth-profiles 格式

### 問題
不要改動 VPS `auth-profiles.json` 裡 minimax / minimax-portal 的格式。

### 正確格式（list + vars）
```json
[
  {
    "id": "minimax",
    "provider": "minimax",
    "vars": { "MINIMAX_API_KEY": "sk-cp-..." }
  },
  {
    "id": "minimax-portal",
    "provider": "minimax-portal",
    "vars": {
      "MINIMAX_OAUTH_TOKEN": "sk-cp-...",
      "MINIMAX_API_KEY": "sk-cp-..."
    }
  }
]
```

### Why
MiniMax provider 透過環境變數注入 API Key，必須用 `vars.MINIMAX_API_KEY`。改成 `key` 格式會導致模型完全無回應。

## 防範原則

1. **新模型接入前**：先確認 TPM 上限
2. **Session Lock**：永遠刪 JSONL，不只是清 sessions.json
3. **記憶目錄**：逐項驗證 AGENTS.md 說的設定是否真的存在
4. **cooldown_time**：litellm 的 cooldown_time = 死鎖陷阱，永遠不要設
5. **auth-profiles.json**：minimax/m... 的 entry 保持原樣不動
