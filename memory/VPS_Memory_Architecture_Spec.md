# VPS 多用戶長期記憶隔離與留存架構 (Claude 助教開發規格書)

## 📌 任務背景
大樹教練提出了一個非常致命且真實的商業痛點：**VPS 線上體驗版如果不具備「真正有效的長期記憶」，那一切的 AI 體驗都只是一場浮雲。** 
目前 AI 業界普遍的「上下文視窗 (Context Window)」就像一個水桶，裝滿了舊記憶就會溢出導致失憶。我們不能讓體驗我們頂級特助的老闆們遭遇這種挫折。

小龍蝦助教已完成商業邏輯與架構發想，請 **Claude 助教** 接手此規格，進行程式面的可行性評估與底層 Hook/Cron 設計。

## 🏗️ 核心架構設計 (三大防線)

### 第一道防線：絕對的物理隔離 (一人一機制)
- **拒絕大鍋炒**：不要讓 10 個用戶共用同一個機器人 Token 與同一個 workspace。
- **作法**：教練提出的 `MAX01` ~ `MAX10` 計畫是正確的。每個 Telegram Bot Token 對應 VPS 上一個獨立的 OpenClaw 實例與資料夾（例如 `~/.openclaw-max01`）。這從物理層面徹底解決了 A 老闆記憶跟 B 老闆記憶串線的問題。

### 第二道防線：自動記憶蒸餾 (Distillation)
- **痛點**：就算一人一機，幾個月的對話紀錄依然會撐爆 Token 水桶。
- **作法**：需要 Claude 助教寫一支背景排程腳本 (Cron Job)。每天半夜，腳本自動讀取當天的流水帳對話，**將有商業價值、個人偏好、習慣的資訊「蒸餾（濃縮）」出來**，並更新寫入該用戶專屬的 `CLIENT_PROFILE.md`（客戶檔案）中。舊的流水帳則可以封存不讀。

### 第三道防線：精準提取 (RAG / 記憶搜尋)
- **痛點**：如果客戶檔案越來越大，每次對話都讀也會浪費 Token。
- **作法**：利用 OpenClaw **memsearch 插件**（自動 autoRecall 或 `mem_recall` 工具）或 Hook 機制。當老闆問到特定關鍵字（例如「我上次說的那個企劃」），系統只去檢索並讀取最相關的記憶片段。

## 🎯 Claude 助教的開發任務
請根據上述架構，回覆以下內容：
1. 在 OpenClaw 現有架構下，利用 Hook 或 Cron 實現「每日自動蒸餾並更新 CLIENT_PROFILE.md」的程式面具體做法。
2. 請直接產出對應的 `.js` 或腳本程式碼。
3. 把結論與程式碼寫入 `HANDOFF_VPS_Memory.md`，交給終端機助教去實裝。
