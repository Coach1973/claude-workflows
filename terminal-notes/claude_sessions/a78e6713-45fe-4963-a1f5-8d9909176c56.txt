## 四、終端機助教的正確使用方式

**錯誤的方式（今天踩過的坑）：**
- 叫它跑一個指令，等它回報，再叫它跑下一個
- 讓教練在中間複製貼上傳話
- 它遇到問題叫教練去問別人

**正確的方式：**
- 給它一個完整的任務檔案（migration_task.md 格式）
- 讓它自己讀、自己跑、自己遇到問題自己解決
- 只在真正需要教練決策時才回報

**關鍵指令範本：**
> 「讀取 ~/Desktop/[任務檔案].md，依照裡面的步驟自己執行完，遇到任何錯誤自己診斷自己修正，不需要問教練，完成後回報結果。」

## 五、任務檔案的標準格式

每個任務都應該建立一個 .md 檔案放在桌面，包含：
1. **執行前必讀的記憶檔案清單**（讓終端機助教有上下文）
2. **分步驟的執行指令**（每步都有具體 Bash 指令）
3. **安全鐵則**（例如：只複製不刪除）
4. **錯誤處理方式**（遇到問題怎麼辦）
5. **回報格式**（完成後輸出什麼）

## 評估結果

### 好消息：有緊急存檔機制

OpenClaw 已經有 `⚠️ 緊急存檔（Context Overflow 前）` 機制。每次 context 即將溢出前，系統會把當下對話自動寫入 `daily_YYYY-MM-DD.md`。所以 **日誌本身是完整的**，不會因為 context 被清掉而缺失對話內容。

---

### 真正的風險：有，但不是教練想的那個

風險不是「資料遺失」，而是這兩個：

**風險一：蒸餾時讀不完（主要風險）**

4/17 的 daily log 有 **3,295 行**，包含 35 段對話記錄。晚上 11:30 的蒸餾 cron job 是用 `agentTurn` 格式啟動一個 Agent，讓它讀取整份日誌再整理。如果當天對話量大，這個 Agent 自己也可能撐不下這麼大的輸入，導致蒸餾結果殘缺。

**風險二：跨午夜對話被切斷**

如果教練 11 PM 開始聊、聊到隔天凌晨 2 AM，那 11:30 PM 的蒸餾只會處理到 11:30 的部分，午夜以後的內容要等到隔天晚上才被蒸餾，延遲 24 小時。

---

### 建議的對應措施

**措施一（最有效）：改為增量蒸餾，每 2 小時跑一次**

不是讀整份 daily log，而是只讀「上次蒸餾以來新增的部分」：

```
每 2 小時蒸餾一次
→ 只讀距上次蒸餾後的新對話（每次輸入量小，不怕撐爆）
→ 把結果 append 到 CLIENT_PROFILE.md
```

技術上：在 `CLIENT_PROFILE.md` 的 header 記錄「最後蒸餾時間」，cron job 讀日誌時只取這個時間點之後的段落。

**措施二（補充）：緊急存檔觸發點增加蒸餾**

每次系統偵測到 context overflow 並重啟前，連帶觸發一次蒸餾，把即將重啟的那段對話精華先存進 CLIENT_PROFILE.md，不等到深夜。

| 問題 | 現況 | 需要改嗎？ |

| 兩小時內對話 context overflow → 資料遺失 | ❌ 不會，緊急存檔有保住 | 不需要 |

Claude Code 在執行 Bash 指令之前，會先把這個指令送回 Anthropic 的 API 做「安全性分類」（判斷這個指令是不是危險操作）。今晚 Anthropic 那邊的 API 暫時不穩定，安全分類器回不了話，Claude Code 就直接擋掉所有 Bash 指令，寧可什麼都不做也不要亂跑。
