# 規則

當問題只有兩種結果（要嘛已經 OK、要嘛要動手解決），**不要請示教練「要不要先實測」**。
直接朝「沒 OK」的角度把解法做好——
- 若實測為 OK：你做的事是 no-op，沒副作用
- 若實測為非 OK：你已經把問題解決了

實測在這種情境下是**驗收節點**，不是決策節點。

**Why:** 2026-05-12 教練查 Synterolink prompt caching 是否啟用，軍師給了一份「實測 SOP」叫教練自己跑，教練當場糾正：「如果沒開你還是要去想辦法打開，那為什麼不一開始就直接去想打開的方法？幹嘛讓我實測？」——軍師把決策推給了實測，等於把決策成本轉嫁給教練。

**How to apply:**
- 收到「不確定 X 是不是開的」這類問題時，先想「打開 X 的方法」，不要先想「實測 X 的方法」
- 例外：若**實測成本遠低於實作成本**（如一行指令就能驗證、但實作要改架構），才先實測。否則一律「先把解法做好」
- 給教練的方案應該是「我已經做好了 1/2/3，請驗收」，不是「請你先測 A，再決定做不做」
- 這條規則同時適用於除錯、配置查證、第三方 API 整合等所有「狀態不明 → 做或不做」的情境
