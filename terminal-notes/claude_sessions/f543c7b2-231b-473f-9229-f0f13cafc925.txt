## 診斷結果：誰吃掉了 3981 字元

**元兇：小龍蝦自己寫的 `TTS_check.js` 測試腳本，加上 session 裡的直接 curl 指令，被反覆執行。**

### 時間軸還原

| 時間 | 事件 |
|------|------|
| 昨天 17:13 | 教練告知「47分鐘後配額重置（約18:00）」 |
| 18:00 | 配額重置，小龍蝦開始嘗試測試 TTS |
| 18:00 以後 | 小龍蝦寫出 `TTS_check.js`，`MAX_ATTEMPTS = 5`，每次最多送 5 次 API 請求 |
| 深夜 | 腳本被多次執行，session 裡另有至少 9 次 `speech-02-hd` 直接 curl 呼叫 |
| 凌晨 2:24 | 已出現 error 2061「配額耗盡或方案不支援」 |
| 今早 | 教練查看：3981/4000，99% 消耗完畢 |

### 關鍵問題：為何沒有產出？

從 session 裡找到這段回傳：
```
"status_code": 2061, "status_msg": "your current token plan not support model, speech-02-hd"
```

**MiniMax 的 `speech-02-hd` 模型需要特定方案才能呼叫。** 但即使 API 回傳錯誤，**MiniMax 仍然在接收請求、計算字元並扣配額**（這是 MiniMax 的計費機制問題）。

數學驗證：
- 每次測試文字 = 51 字元
- `TTS_check.js` 每次執行最多 5 次 = 255 字元
- 3981 ÷ 255 ≈ **需要跑 16 次腳本**（或等效的 78 次單次呼叫）
- 完全符合「腳本被反覆執行」的模式

### 結論

**沒有任何語音輸出，但 3981 字元被吃掉**，原因是：
1. 小龍蝦反覆呼叫 TTS API 測試「配額有沒有恢復」
2. MiniMax 在處理請求時就扣配額，即使最終輸出失敗或模型不支援
3. 這是一個典型的「測試行為本身造成消耗」問題

  核心原則

  Telegram bot 無法可靠地互相讀取，所以 bot-to-bot 任務傳遞必須用 sessions_send，不能用自由格式訊息。

  ---
  sessions_send 完整語法

  HANDOFF
  from: <發送方 agent-id>
  to: <接收方 agent-id>
  task_id: <短唯一識別碼>
  priority: P0|P1|P2
  summary: <一行任務摘要>
  context: <相關事實、連結、路徑、分支、限制>
  deliver_to: telegram:<group-id>:<topic-id>
  deadline: <ISO 時間戳 或 "asap">
  done_when:
  - <完成條件1>
  - <完成條件2>

  ---
  ACK / DONE / BLOCKED 格式

  ACK（接收方，2分鐘內回）
  ACK <task_id> — accepted
