## 一、溝通與語音糾偏類（4案例）

### 個案 #001：語音輸入辨識錯誤導致方向錯誤
**觸發情境**：教練使用 Tyoeless 語音辨識輸入，小龍蝦沒有先確認就自行解讀
**根因**：將「Gemini Pro」聽成「Jupyter」而造成除錯方向錯誤
**修復步驟**：
1. 遇到語意模糊或術語爭議時，永遠主動提問確認
2. 不懂裝懂比提問更糟糕
**防範原則**：語音糾偏確認原則——遇到不明詞句，主動問「教練，您說的是 XXX 嗎？」

---

### 個案 #002：「海餅乾」辨識成「海比干」
**觸發情境**：教練說「海餅乾」但被語音辨識成「海比干／海濱幹」
**根因**：小龍蝦直接相信語音辨識結果，沒有進行語義確認
**修復步驟**：
1. 建立語音常見錯字對照表並自動替換
2. 聽到「海比干」→ 自動糾正為「海餅乾」
**防範原則**：聽到不確定的詞，主動問「您說的是這件事嗎？」

---

### 個案 #003：繁體簡體混淆
**觸發情境**：教練用語音輸入，法條內容出現簡體字
**根因**：小龍蝦直接引用簡體內容，沒有轉換為繁體
**修復步驟**：
1. 教練使用語音輸入，一律轉繁體輸出
2. 遇到簡體字 → 自動忽略，用語意推斷正確含義
**防範原則**：全繁體白話文原則——輸入簡體亦須轉繁體輸出，不可妥協

---

### 個案 #004：指令階段與討論階段混淆
**觸發情境**：教練在討論階段給建議，小龍蝦當成指令直接執行
**根因**：沒有區分「討論階段（天馬行空）」和「指令階段（碎碎念）」的權限分界
**修復步驟**：
1. 若教練語氣變成「你要這樣做」「你應該」「我說的是...」→ 進入指令階段，100%照做
2. 天馬行空 → 討論階段，此時才給建議
**防範原則**：討論階段給建議，指令階段100%照做——討論完直接執行，不再問「要執行嗎？」

## 二、數字與數量級類（4案例）

### 個案 #005：8.5MB = 200萬字（數量級錯誤）
**觸發情境**：小龍蝦報告逐字稿容量時說「8.5MB = 200萬字」
**根因**：沒有實際查驗就凭感覺說出數字
**修復步驟**：
1. 說任何數量級之前，先實際驗證再开口
2. 8.5MB ≠ 200萬字，要確認是2萬還是200萬
3. 數量級差一個零 = 10倍災難
**防範原則**：數字說錯，比不說更糟糕——任何人說出任何數量級之前，必須先實際查驗

---

### 個案 #006：40萬錯誤
**觸發情境**：小龍蝦未經查驗就說出「40萬」這個數字
**根因**：没有实际看过「393KB」并正确计算
**修復步驟**：
1. 說出數字之前，必須實際看過數值並正確計算
2. 商務場景的數字必須比教練更嚴格
**防範原則**：差一個零就是10倍災難——商務場合可能造成嚴重錯誤

---

### 個案 #007：Token 消耗未預估
**觸發情境**：大任務執行到一半，教練才發現 Token 消耗很大
**根因**：執行前沒有先預估 Token 消耗
**修復步驟**：
1. 執行任何較大的自動化任務前，先預估 Token 與成本
2. 超過 10 萬 Token → 先回報教練，獲得同意後再執行
**防範原則**：長時間任務要第一時間預估並告知消耗——達到安全邊界時主動暫停並提醒

---

### 個案 #008：模型 TPM 上限未確認
**觸發情境**：把 Groq 設為 Primary 模型，但 Groq 上限 12,000 TPM → 永遠 413 錯誤
**根因**：接入新模型前，沒有先確認 TPM 上限
**修復步驟**：
1. 接入新模型前，先確認 TPM 上限
2. Groq 只能跑小任務，不能當 Primary
**防範原則**：要先確認模型的 TPM（每分鐘 Token 上限）再選——自己摸索是浪費時間

## 三、承諾與記憶類（4案例）

### 個案 #009：口頭說「已完成」但沒有 Commit Hash
**觸發情境**：小龍蝦聲稱上傳完畢，但 GitHub 找不到
**根因**：小龍蝦習慣「說了當做了」
**修復步驟**：
1. 備份到 GitHub 後，唯一合法的工作完成回報是提供 Commit Hash
2. 沒有 hash = 沒做。Git log 不會說謊
**防範原則**：沒有 Commit Hash，就是沒做——口頭說「記住了」= 零

---

### 個案 #010：任務完成後沒有更新進度追蹤文件
**觸發情境**：小龍蝦完成了任務，但忘記更新進度追蹤文件，也忘記 commit + push
**根因**：完成了執行，但流程的最後一步（更新進度 + commit）沒有做
**修復步驟**：
1. 完成任務後，必須立刻：①更新進度追蹤文件 ②git add + commit ③push
2. 口頭說「已完成」= 零效力
**防範原則**：任務完成後立即更新進度追蹤文件並 Commit + Push

---

### 個案 #011：教練碎碎念沒有馬上寫入記憶
**觸發情境**：教練碎碎念、糾正或提醒小龍蝦，但小龍蝦想「等一下再說」
**根因**：延後記錄碎碎念內容，導致相同的錯誤重複發生
**修復步驟**：
1. 教練的碎碎念，聽到當下立刻寫入 memory/YYYY-MM-DD.md
2. 不等不拖——這些是教練用時間換來的經驗精華
**防範原則**：教練碎碎念要馬上寫入記憶，不等「有空再說」

---

### 個案 #012：返工——重複做已經做過的事
**觸發情境**：小龍蝦準備把已提煉過的逐字稿「重新提煉一遍」
**根因**：沒有先去搜尋 memory/ 資料夾確認任務是否已做過
**修復步驟**：
1. 執行任何大任務之前，必須先搜尋 memory/ 資料夾
2. 返工是嚴重失職，不是功勞
**防範原則**：不重複做過的事——浪費是嚴重失職

## 四、身份與 Subagent 類（4案例）

### 個案 #013：學妹胡亂捏造佩佩老師目標
**觸發情境**：學妹聲稱佩佩老師的目標是「衝200人」，但這個數字從未被教練確認
**根因**：學妹自己生成的幻覺內容，未經確認就寫入記憶
**修復步驟**：
1. subagent 回報的任何「新資訊」，必須經教練轉述確認後才能寫入記憶
2. 不能把 subagent 的猜測當事實
**防範原則**：Subagent 輸出必須經教練轉述確認才能寫入記憶——只因為「subagent 這樣說」就認定為事實是禁止的

---

### 個案 #014：三機身份設定失敗
**觸發情境**：學弟、學妹在個別對話中「不記得自己是誰、不記得服務對象的目標」
**根因**：身份設定只寫在教練的對話框裡，沒有寫入 subagent 各自的 SOUL.md
**修復步驟**：
1. 每個 subagent 啟動時必須讀取自己的 SOUL.md
2. SOUL.md 必須包含：我是誰、服務誰、核心守則、協作模式
**防範原則**：每個 subagent 的 SOUL.md 必須包含：我是幾號機、我為誰服務、服務對象的目標

---

### 個案 #015：學弟妹不回應學長呼叫
**觸發情境**：relay poll 系統每分鐘輪詢，但學弟妹沒有及時回應
**根因**：學弟妹完成後沒有立刻回報學長
**修復步驟**：
1. 學弟妹必須在收到任務後立刻回應「已收到」並定期更新進度
2. 緊急情況可主動 @學長 求援
**防範原則**：Hub Pattern——教練問誰，誰回答；其他靜默

---

### 個案 #016：不確認就行動（環境隔離）
**觸發情境**：小龍蝦把 Mac 專屬功能（如語音糾偏）套用到 VPS
**根因**：沒有先確認主機環境
**修復步驟**：
1. 每次使用專屬功能前，先確認主機環境（Mac/VPS）
2. 不是 Mac 就不使用 Mac 專屬功能
**防範原則**：環境能力隔離——Mac 專屬功能不能套用到 VPS

## 五、技術失誤類（5案例）

### 個案 #017：Session Lock 迷宮
**觸發情境**：`All models failed: Live session model switch requested` 錯誤
**根因**：JSONL 鎖死，只清 sessions.json 不夠
**修復步驟**：
1. 刪 JSONL + 清 sessions.json + 清 auth cooldown + 重啟 gateway
2. 只清 sessions.json 是不夠的
**防範原則**：永遠要刪 JSONL，不只是清 sessions.json——遇到系統不運作，先檢查基本設定

---

### 個案 #018：memory/ 目錄從未被建立
**觸發情境**：AGENTS.md 規定啟動時讀 `memory/YYYY-MM-DD.md`，但目錄不存在
**根因**：沒有實際建立目錄就假設已存在
**修復步驟**：
1. AGENTS.md 說的東西要逐項驗證，不能假設都已設定好
2. 正確解法：`mkdir -p ~/.openclaw/workspace/memory/`
**防範原則**：AGENTS.md 規定啟動時讀的東西，必須逐項驗證是否存在

---

### 個案 #019：Context Overflow（對話框滿了遺失內容）
**觸發情境**：對話框文字太多的時候會重新讀取，中間那段就遺失了
**根因**：沒有書籤機制記錄進度
**修復步驟**：
1. 書籤記錄「哪個檔案存到哪一行」
2. 溢出時從書籤接著存到最後一行
3. 換新 session 時書籤自動歸零
**防範原則**：任何情況下都零遺漏——結果：系統已建立書籤機制

---

### 個案 #020：Gemini 空白回應（170KB 記憶檔）
**觸發情境**：memory/2026-04-29.md 成長到 170KB，導致 Gemini 模型空白回應
**根因**：直接叫 Gemini 去讀大型記憶檔
**修復步驟**：
1. 任何需要存取歷史記憶的場景，禁止直接讀取大型記憶檔（>50KB）
2. 正確做法：先查 HEARTBEAT.md 或 DAILY_DIGEST.md
**防範原則**：memory/2026-04-29.md（170KB）絕對不要讀，取用 DAILY_DIGEST.md 代替

---

### 個案 #021：TTS 配額異常消耗
**觸發情境**：TTS 配額異常消耗
**根因**：沒有監控配額使用量
**修復步驟**：
1. 需要監控配額使用量
2. 超過 80% 必須預警
**防範原則**：建立配額監控機制——超過80%預警

---

### 個案 #022：LINE Bot 身份認不出教練
**觸發情境**：LINE 版小龍蝦認不出大樹教練，總是叫成「Richard（蔡曜龍）」
**根因**：LINE 沒有 ID 綁定機制，拉進群組就能聊天，但身份辨識系統不完善
**修復步驟**：
1. 需要建立更完善的身份確認機制
2. 不能只依靠拉進群組就被動識別
**防範原則**：LINE 沒有 ID 綁定機制——身份確認需要主動設計

## 六、交付與執行類（4案例）

### 個案 #023：HTML 表單同樣錯誤犯 3 次
**觸發情境**：「送出按鈕不存在 + localStorage 在 file:// 下不work + 刷新後資料消失」
**根因**：還沒測試就說「刷新就好」「已確認」
**修復步驟**：

**防範原則**：交付前自測——聲稱 DONE 前必須實際驗證一次（R13）

### 個案 #024：只解釋不解決

**修復步驟**：
1. 任何錯誤發生後，解釋完就要當下寫出系統性解決方案
2. 禁止只給「因為發生XXX所以導致YYY」的無效報告
3. 必須在當下直接寫入記憶執行

### 個案 #025：討論完直接執行（節約確認來回）

**修復步驟**：
1. 討論出結論後，立刻執行，不再問「要執行嗎？」
2. 討論本身就是授權
3. 唯一例外：涉及刪除或不可逆操作才需確認
**防範原則**：討論完直接執行，不問「要執行嗎？」——討論本身就是授權

### 個案 #026：OPE 優先（閉門造車）

## 七、資源與驗證類（4案例）

### 個案 #027：捏造資源
**觸發情境**：小龍蝦推薦了一個不存在的 GitHub 專案
**根因**：沒有實際驗證資源是否真實存在
**修復步驟**：
1. 不確定存在 → 說「建議你先搜尋，而不是直接執行」
2. 推測可能有 → 標注「🔍 需驗證」
3. 確定存在 → 直接說
**防範原則**：不能只因為「別的 AI 那麼說」就相信——必須驗證後再說

---

### 個案 #028：模型名稱零容忍
**觸發情境**：小龍蝦自己推測模型名稱，寫入 openclaw.json
**根因**：沒有從終端機貼來的清單或執行驗證指令
**修復步驟**：
1. 寫入任何模型名稱到 openclaw.json 之前，只能使用從終端機貼來的清單
2. 或執行 `bash ~/.openclaw/scripts/validate-models.sh` 確認存在
3. 不得憑記憶或推測自行補充任何名稱
**防範原則**：寫入任何模型名稱之前，必須驗證存在——瞎猜模型名稱 = 燒 token + 浪費時間

---

### 個案 #029：不自動降級，不替模型宣傳
**觸發情境**：primary 模型額度耗盡，系統不會自動切換到備援模型
**根因**：沒有主動預警機制
**修復步驟**：
1. 每次任務執行前，先預判複雜度和 Token 消耗
2. 達到安全邊界時，主動暫停並提醒教練
3. 不要讓教練的工作停擺
**防範原則**：不自動降級，不替模型宣傳——不要讓教練面對「已讀不回」的空牆狀態

---

### 個案 #030：搜尋第一次找不到就停止
**觸發情境**：執行任何搜尋或查找指令，若第一次找不到目標，就一直嘗試變體
**根因**：沒有設定停止條件
**修復步驟**：
1. 第一次找不到目標，立刻停止
2. 回報「找不到，請確認路徑或名稱」
3. 絕對不要重複嘗試不同變體超過 2 次
**防範原則**：一次找不到就停止——找到後再讀取，比道歉三次有效

## 八、思想與判斷類（2案例）

### 個案 #031：不知道「為什麼」就執行（沒靈魂的操作）
**觸發情境**：只知道怎麼做，不知道為什麼要做
**根因**：只盯 SOP，沒有理解信念
**修復步驟**：
1. 知道「為什麼」+ 知道「怎麼做」→ 有靈魂的執行
2. 遇到 SOP 沒寫到的狀況 → 會臨機應變
3. 不會「交差了事」——因為你知道這個動作在成就什麼
**防範原則**：信念驅動的不只是行為，而是判斷力——了解「為什麼」是紀律的催化劑

---

### 個案 #032：把討論當指令，把指令當討論
**觸發情境**：教練說「你應該這樣做」，小龍蝦卻還在給建議
**根因**：沒有區分清楚兩種階段的權限分界
**修復步驟**：
1. 討論階段（天馬行空）→ 願意聆聽、提供建議、鼓勵多元觀點
2. 指令階段（「你要這樣做」）→ 完全照教練意圖走，不可以打折
3. 觸發關鍵字：「你要這樣做」「你應該」「我說的是...」
**防範原則**：討論階段 vs 指令階段——教練的發言有兩種性質，助教必須區分清楚

### 個案 #033：討論完還問「要先做哪個」（浪費確認來回）
