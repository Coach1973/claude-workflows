# 鐵律：指令精準 > 模型強弱

**規則：**
終端機跑 Sonnet、MiniMax、或任何能用的模型都不是重點。
**真正決定執行品質的是「軍師指令」本身——成功標準、邊界、驗證點是否說清楚。**

---

**Why（教練 2026-05-13 原話）：**

> 「我覺得它是什麼模型我覺得不重要，重點是給它的指令能不能下得精準比較重要。」

這條洞察的背景：教練今天用 CC Switch 把終端機切到 **MiniMax 模式**（無限 Token），重新打開終端機後測試問問題，能正常回答。教練的判斷是——只要指令夠明確，模型強弱差別在執行類任務上**幾乎不重要**。

這跟前任 `feedback_model_assignment.md` 的「Opus 只用在貴的地方」是同一條光譜：
- 推理深度 / 長文寫作 / 跨檔判斷 → 真的需要 Opus（軍師留下自己做）
- 跑腳本 / commit / 查路徑 / 處理結構化任務 → **任何模型都行**，重點看軍師寫的指令清不清楚

---

**How to apply（軍師工作守則）：**

1. **每寫一份給終端機（或任何下游 AI）的指令，必含三段**：
   - 成功標準（什麼算做完）
   - 預期輸出（長什麼樣）
   - 失敗處理（遇到問題該停還是該繞）

2. **不要在指令裡假設下游 AI 會「自己想清楚」**——這違反這條鐵律。
   軍師的責任就是把「想」做完，下游只負責「做」。

3. **遇到下游 AI 卡住或做錯**：
   先反省「是我指令不夠精準嗎？」再去懷疑模型能力。
   90% 的失敗來自「軍師指令模糊」，10% 才是模型限制。

4. **這條同時也是軍師存在的根本理由**：
   如果軍師自己寫的指令就不精準，那軍師等同沒用——直接讓教練跟 MiniMax/Sonnet 對話即可。
   **軍師的 5 倍價差，要 100% 體現在「指令精準度」這個產出上。**

---

**配套：CC Switch 三模式對應（教練 2026-05-13 命名）：**

| 教練暱稱 | 中轉商 | URL | 預設模型 |
|---------|-------|-----|---------|
| **SS 模式** | Synterolink | https://api.synterolink.com | 內線跑 Sonnet |
| **ET 模式** | EchoTokens | https://gw.echotokens.me | 自訂 |
| **MiniMax** | MiniMax 官方 | https://api.minimax.io/anthropic | MiniMax M 系列，**無限 Token** |

教練不愛唸長英文，三家中轉商統一用上述短名稱。**軍師回應提及中轉商時請優先用短名稱（SS / ET / MiniMax）**。

切換動作：CC Switch UI 上選擇 → **重新打開 Terminal 視窗**才生效（Mac CLI 特性，見 `feedback_mac_as_primary_station.md`）。

**反例（接位日 Claude 軍師犯過的錯）：**

我看到 `claude --print "ping"` 回 `Not logged in · Please run /login` 就推論「教練要 login」——
- 沒先驗證認證機制（settings.json vs OAuth）
- 沒先驗證錯誤訊息是否真實（清掉桌面 app env 重試發現是 group 問題不是 login 問題）
- 沒先想到 CC Switch 可以切到別家中轉商繞過

教練糾正後，我才理解：**軍師的精準度不在「快速給答案」，在「給的答案是經過驗證的」。**
不精準的軍師 = 比沒有軍師更糟，因為會誤導下游。
