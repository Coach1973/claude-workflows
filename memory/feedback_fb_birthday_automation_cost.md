# FB 生日自動化：成本與技術路線評估 (2026-04-12)

## 背景
教練敏銳指出：為了發送一句 FB 生日祝福，單次消耗數萬 Token 在商業上對終端客戶是不合理的。因此暫停此功能的全量開發，改為「壓力測試用途」。

## GitHub 競品與技術路線對比
透過檢視開源社群（如 Puppeteer, Selenium 寫的 Facebook Birthday Bot），目前有兩條技術路線：

### 1. 傳統爬蟲/RPA (目前 GitHub 上的主流)
- **作法**：寫死按鈕的程式碼位置（例如：`點擊 class="xyz-123" 的按鈕`）。
- **優點**：Token 消耗為 **0**。速度極快。
- **缺點**：極度脆弱（Brittle）。FB 為了防機器人，每隔幾週就會隨機更動底層的 class 名稱。一旦 FB 改版，程式直接報廢，必須等工程師修復。這會導致客戶「踩坑」，違反頂級特助 UX 守則。

### 2. LLM 視覺/DOM 代理 (我們目前的作法)
- **作法**：把整個網頁結構丟給 AI，讓 AI 像真人一樣「看懂」哪裡是發送按鈕。
- **優點**：無視 FB 改版，具備極強的抗打擊能力。
- **缺點**：Token 消耗極大（單次任務數萬 Token）。

## 商業決策與未來展望
教練的決策非常精準：**現階段將這項功能封存（保留為手動/半自動模式）**。
隨著 AI 算力成本每幾個月就腰斬一次，未來這類「高耗能但高穩定性」的智慧型 RPA 將會成為白菜價。在此之前，不輕易把這種高耗能功能端給客戶，保護客戶的錢包。
